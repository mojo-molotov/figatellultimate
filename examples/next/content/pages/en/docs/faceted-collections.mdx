# Faceted collections

A faceted collection filters a list by several facets, sorts it and paginates it, with its whole state in the URL: a filtered view is a link anyone can share, and the default view is prerendered.

## The engine

`defineFacetedCollection` declares the items, their facets and sorts, and the page size. The engine is pure: it reads a URL, computes a view, and writes the next URL.

```ts
import { defineFacetedCollection } from '@figatellultimate/facets';

const engine = defineFacetedCollection({
  items: posts,
  key: (post) => post.url,
  facets: { tags: { values: (post) => post.tags }, authors: { values: (post) => post.authors, mode: 'all' } },
  sorts: {
    'date-desc': (one, other) => other.date.localeCompare(one.date),
    'title-asc': (one, other) => one.title.localeCompare(other.title),
  },
  perPage: 5,
});

const state = engine.read('?tags=release&sort=title-asc&page=2');
const { keys, total, pages, counts } = engine.view(state);
```

| Piece                       | Role                                                                                                             |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `read(search)`              | The state of any URL: an unknown value, a page out of range or a broken link give a valid state, never an error. |
| `view(state)`               | The visible keys, the total, the pages, and each value’s count.                                                  |
| `transition(state, action)` | The next state and its URL, for `toggle`, `clear`, `sort` or `page`.                                             |
| `write(state)`              | The canonical URL of a state.                                                                                    |

The page and the sort are read from `page` and `sort` in the query; `params: { page: 'p', sort: 'order' }` names them otherwise, never as a facet.

A facet in `any` mode keeps an item carrying one of the checked values; in `all` mode, every one. Facets combine with AND.

### Where the page lands

Changing a filter keeps the reader’s place by default (`keepReadingPosition`): the page holding the first post they were looking at. `backToFirstPage` goes back to page 1 instead.

## In React

`useFacetedCollection` binds the engine to the URL; the components are unstyled and accessible:

```tsx
import { FacetOptions, FacetsReset, Pagination, SortSelect, useFacetedCollection } from '@figatellultimate/facets-react';
import { useNextUrl } from '@figatellultimate/next16/facets';

const binding = useFacetedCollection(engine, useNextUrl());

<FacetOptions binding={binding} facet="tags" labels={labels.tags} locale="en" />
<SortSelect binding={binding} labels={labels.sort} />
{binding.view.keys.map((key) => cards[key])}
<Pagination binding={binding} labels={labels.pagination} locale="en" />
```

`PageSelect` is a compact pagination, the pages as a select, for a toolbar; the full `Pagination` keeps the links. Each takes `icons` for previous and next, shown alone on a narrow screen.

`ListingOptions` puts the facets behind one button, the app’s icon (a gear) and the count of selected terms: its panel holds the widgets as they are, ↑ and ↓ moving from one to the next, so that a listing’s controls keep one line on any screen, the sort beside the gear. A single facet shows in the gear’s place: a panel holding one list would be a click for nothing.

Each text read aloud may differ from the one seen, when the latter reads badly: `spoken` of `SortSelect` reads “Alphabetical order” for `A → Z` (the open list shows it too, an option’s name holding its visible text), `spoken` of `PageSelect` reads “Page 3 of 10” for `3 / 10`, and `unit` of `FacetOptions` makes “Harp 17 posts” heard under “Harp 17”.

`useNextUrl` changes the URL through the History API, integrated by Next’s router: no server request per filter. Outside Next, `useHistoryUrl` does the same.

The hook gives keys only: the application renders its cards once, on the server, and shows the ones the view holds.

### Paginated listings

A listing whose pages are prerendered (`perPage` of `folderPages`) sends each page with its slice alone: `/blog/news/page/2` holds its five posts, whatever the blog’s size. Its default pages live in the path, reached through the router. A filter or a sort stays in the query (`/blog/news?tags=bot`) and needs every post of the listing, from any page: the browser computes it from the listing’s index, a static JSON fetched on the first filter or sort, never with the page.

`usePagedCollection` passes the listing’s first page’s URL and does the orchestration: the page’s slice until the index is needed, its default pages reached by the URL alone, the index prefetched as the reader heads for a filter (`prefetch`, on the pointer or the focus), a filter chosen early applied once it is here. `createIndexLoader` checks the index by your schema before it is read, and fetches it once per listing.

```tsx
const load = createIndexLoader((json) => v.parse(Index, json));
const { binding, index, prefetch } = usePagedCollection({
  engine: postsEngine,
  items: slice,
  paged: { page: folder.page, pages: folder.pages, total: folder.entries.length },
  load: () => load(indexUrl),
  url: useNextUrl({ first: folder.first }),
});
```

The config declares where the indexes live: `index` in `folderPages` for a collection’s listings, in a taxonomy’s `pages` for its terms. Each page of a paginated listing then carries its index’s URL (`folder.index`, `page.index`), the same on every page, and the generated code lists the listings to index (`blogListingIndexes()`, `authorsListingIndexes()`).

```ts
folderPages: { levels: ['category', 'subcategory'], perPage: { subcategory: 5 }, index: 'listing' },
```

The index is one static route per listing and locale, from `listingIndexRoute` of `@figatellultimate/next16/listing-index`, which takes those listings, each one’s route parameters, and `build`, its content: each post’s item, what the engine filters and sorts, and its card’s data, so that the browser draws the cards of the pages it does not have. Only `build` is the app’s to decide.

```ts
// app/[locale]/listing/[[...folder]]/route.ts: /listing/news/bot, /en/listing/news/bot
export const dynamic = 'force-static';
export const dynamicParams = false;
export const { GET, generateStaticParams } = listingIndexRoute({
  listings: blogListingIndexes,
  params: (folder) => ({ locale: folder.locale, folder: Object.values(folder.segments) }),
  build,
});
```

The example has two: `listing/[[...folder]]` for a subcategory’s posts, `author-listing/[...term]` for an author’s, across every subcategory. An index costs about fifty bytes gzip per post (the load test measures it).

Next to its index, a listing has page batches: its default view’s pages in runs of ten (`batchesOf`), each a small static file at `<index>/pages/<first page>`, built by the same route (its `pages` option). `usePagedCollection` loads the current page’s batch once the page is idle, then the next or previous one near its edges; a page its batch holds is shown at once, only the address moving, and any other goes through the server. The cost per visit stays a batch’s, about two kilobytes gzip, whatever the list’s length: the load test measures a click on next at under 50 ms with the server 300 ms away, against 360 ms through the server.

```ts
usePagedCollection({ …, batches: { load: (from) => loadBatch(`${index}/${batchPath(from).join('/')}`) } });
```

`pageItems` and `batchItems` of `@figatellultimate/facets` give a page’s items and a batch’s, for its `build`. In a prerendered page, `NextUrlBoundary` of `@figatellultimate/next16/facets` renders the listing from its landed page while the address is unread, then from the address: the pagination’s links are real in the HTML. The locale switcher follows the page a batch shows: `usePagedLocaleLinks`, with the listing in each locale (`listingLocalesOf` of `@figatellultimate/site`).

Folder pages have their batches too: the blog and a category, their subfolders’ sections ten pages at a time. Each paginated folder carries its batches’ URL under the indexes’ prefix (`folder.batches`: `/listing`, `/listing/news`), the generated code lists those folders (`blogFolderBatches()`), and the route serves them through `pages.listings`; hence the optional catch-all, for `/listing/pages/1`. A folder has nothing to filter: `usePagedCollection` does without an index there (no `load`).

Outside Next, `pagedHref` and `pagedSearch` of `@figatellultimate/facets` map a view to this location and back. With a page segment other than `page` (`urls.page`) or a page parameter of the engine’s own (`params.page`), `useNextUrl`, `NextUrlBoundary` and `usePagedLocaleLinks` take them as `segment` and `param`: the generated `pageSegment` of `#figatellultimate/urls` gives the first.

### Responsive section batches

A section index such as `/docs` can split its cards into static JSON batches with `splitSectionBatches` and `pagedSectionsOf` from `@figatellultimate/site` (served through `listingIndexRoute`), and render them with `ResponsiveBatchList` and `BatchPagination` (or the `useResponsiveBatches` and `useBatchPagination` hooks) from `@figatellultimate/facets-react`: progressive scroll loading (`IntersectionObserver`) on phones and classic pagination (`PageSelect` + `Pagination`) on desktops, sharing one batch cache and the same prerendered HTML.
